## Exact changes

One new forward-only migration, generated by official Supabase CLI **2.120.0**:

`supabase/migrations/20261013205746_permanent_free_subscription.sql`

The migration runs inside `BEGIN`/`COMMIT`. It changes schema/functions/policies only; applying it performs **no backfill or rewrite of existing data rows**. All 45 historical migration files remain unchanged. Their replay occurred only inside fresh isolated test databases, never by reapplying them to an existing or production database.

### Permanent Free and retained history

- New subscription defaults are `plan='free'`, `status='free'`, `trial_used=false`.
- New Free shops receive `expires_at=NULL`; no new `trial_grants` entry is created. The legacy shop trigger name is retained to minimize changes.
- `expires_at` becomes nullable only for properly formed Free rows. Paid/non-Free rows still require an expiry through a CHECK constraint.
- A nullable `paid_starts_at` column records the actual start of later paid activations without destroying original `started_at` or `trial_ends_at` fields. Existing rows receive no backfill; legacy scheduled paid plans continue using their original stored dates.
- Existing trial rows/ledger remain intact. They are interpreted as effective permanent Free rather than deleted, reset or given a new trial. Original trial-only dates/status remain readable as history in the base tables.
- Existing paid/grant/payment records, paid expiry dates, schedules and `grace_days` are unchanged by the migration.
- Missing subscription metadata fails closed rather than inventing a new entitlement.

### Storage and image rules

- `app.free_product_limit()` is now five; `app.free_image_limit()` remains five.
- Storage counts every product row regardless of active/hidden/archived status or everyone/profile visibility. Hiding/archiving does not release capacity. Actual seller deletion does.
- New inserts and shop transfers take the subscription row lock before counting, coordinating with subscription changes and the existing 1,000-product trigger. Same-shop edits to retained over-quota products remain permitted.
- The paid 1,000-product ceiling is retained. Existing image trigger/gallery RPC/position constraints remain unchanged; actual PostgreSQL tests confirm five images, sixth-image refusal and gallery reordering/upsert behavior.
- No product, image, account, shop, payment or R2 deletion is part of this migration. Existing explicit seller deletion behavior remains available; tests verify that it releases a slot.

### Paid expiry, public visibility and re-upgrade

At paid expiry the **storage tier** becomes Free. Existing paid **public visibility continues through the exact stored grace period**. This preserves the latest owner's explicit grace requirement: it deliberately does not truncate an existing grace window to five public products.

After grace ends, up to five seller-active products are publicly eligible, selected across the whole shop by:

`sort_order ASC, created_at DESC, id ASC`

The same five are selected before category/search/Home filters. A profile-only product still participates in the five and is subsequently excluded from Home. Anonymous and other authenticated users share the same selection; existing owner/admin reads still see retained rows.

This is a read-time RLS predicate. Expiry changes **no product status, visibility preference, gallery, ordering or image key**. The historical mutating `app.demote_to_free_limit()` is retired: execution grants are removed and even a privileged invocation raises `SW009` instead of writing product rows.

An upgrade removes the quota predicate from eligible active products. Seller-hidden/archived products stay hidden/archived; Home visibility choices remain intact. Already-hidden historical products are not automatically reactivated because the reason for their hiding is not reliably recorded.

The expiry sweep still marks lapsed paid subscriptions expired, preserving their plan/date/grace metadata. It ignores history-only unpaid trials and independent restrictions. Public fallback does not depend on the sweep running.

Shop status suspension/ban and subscription suspension take precedence over publishing/public-product entitlement. Paid activation now refuses a restricted shop with `SW005` instead of clearing subscription suspension. Existing owner read/edit privileges are preserved; an edit cannot bypass the public restriction. The existing public-header behavior is unchanged: shop suspension/ban removes the header, while subscription suspension makes `products_visible=false` but can leave the independently active contact header accessible.

### Payment boundary

Wayl Worker code, checkout, verification, webhook/event dedupe, intent lifecycle/reuse, anti-stacking checks, prices and provider settings are unchanged.

`admin_apply_payment()` keeps its existing caller interface, authorization/ACL/search path and payment recording. Its calendar now distinguishes unpaid Free/history from a held paid entitlement:

- New purchase on Free starts at verified database activation time, even if a historical trial deadline remains in the future.
- An existing held paid administrative extension retains its current extension base and schedule.
- Original `started_at` and `trial_ends_at` are not cleared/reset; new actual start is stored separately.
- `grace_days` is not changed.

The existing two public prices remain **5,000 IQD** and **9,000 IQD**. Historical/manual `month_1` remains supported; a new public Wayl one-month intent remains rejected.

`subscription_state()` retains its existing return-column shape, but reports effective Free without expiry/countdown. Existing scheduled paid plans/grace and restrictions remain distinguishable for the future Worker phase.
